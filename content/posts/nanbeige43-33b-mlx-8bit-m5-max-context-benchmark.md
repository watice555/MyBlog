# Nanbeige4.3-33B MLX 8bit 测速：M5 Max 上的 8K–128K 上下文

在 Apple M5 Max、128 GB 统一内存的机器上，Nanbeige4.3-33B MLX 8bit 的生成速度，从 8K 输入时的 **14.45 tokens/s**，下降到 128K 输入时的 **5.92 tokens/s**。128K 档完整处理输入耗时约 **11 分 19 秒**，MLX 峰值分配约 **59.93 GiB**。

这是 2026 年 10 月 26 日的一轮本机吞吐测试。四个档位都使用《红楼梦》连续中文正文，每档独立进程、空 KV 缓存，固定生成 128 tokens。这里记录的是原始文本续写速度，没有运行聊天服务、代码 Agent 或能力榜单，也没有测长文问答准确率。

## 测试环境与权重

| 项目 | 本次配置 |
| --- | --- |
| 硬件 | Apple M5 Max，18 核 CPU、40 核 GPU、128 GB 统一内存 |
| 系统 | macOS 27.0.1，arm64 |
| 模型 | Nanbeige4.3-33B 的 MLX 8bit 转换权重 |
| 权重量化 | affine 8bit，group size 64 |
| 权重分片总大小 | 35,189,757,302 字节，约 32.77 GiB |
| 推理实现 | 直接调用 MLX-LM 模型，Metal 后端，单并发 |
| 软件版本 | MLX 0.32.0、MLX-LM 0.31.3、Transformers 5.12.1 |
| KV 缓存 | BF16，未量化，不滑动截断上下文 |
| 输入处理块 | 2,048 tokens |
| 解码 | 贪心选择非 EOS token，固定 128 次解码计算，无 MTP 或草稿模型 |
| 电源 | 插电，使用 `caffeinate -i` 防止空闲睡眠 |

原模型来自 [Nanbeige/Nanbeige4.3-33B](https://huggingface.co/Nanbeige/Nanbeige4.3-33B)，本机使用 [fcmeyer 的 MLX 8bit 转换版本](https://huggingface.co/fcmeyer/Nanbeige4.3-33B-MLX-8bit)。转换包记录的上游 revision 为 `c1093c501cc6460427c0ac634db7223d0450c0ee`。权重量化和 KV 缓存精度是两件事：本文的“8bit”指权重，KV 仍然使用 BF16。

正式数据来自 16:29:51–16:47:16（Asia/Shanghai）的插电重测。此前短试跑后发现电源脱落，因此停止旧轮次，重新从 8K 开始；旧数据没有混入本次表格。

## 语料与输入长度

语料沿用此前 DeepSeek 测速所用的《红楼梦》连续正文，来源为 [Project Gutenberg 的版本](https://www.gutenberg.org/ebooks/24264)。既有语料已去除站点头尾和前言、统一换行并转为简体，不靠重复短句填满上下文。本次直接读取这份文件，没有重新下载或改写正文。

语料文件的 SHA-256 为：

```text
61de8bff3908b08422bcd354273ef6db58d795006ded2ec9c54b912edf9307da
```

Nanbeige 分词后，全篇共有 666,930 tokens。每档从同一篇正文开头截取精确数量的 token，不添加 BOS 或聊天模板等特殊 token；四档分别为 8,192、32,768、65,536 和 131,072 个输入 tokens，按此顺序运行。最大档对应解码后的正文约 172,678 个字符。

复用语料可以减少文本内容的差异，但不同模型的分词器仍可能把同一段文字切成不同数量的 token。因此，“相同 token 数”不保证覆盖相同字符数，不能把它当成完全等量的跨模型中文阅读任务。

## 计时口径

每档启动一个新进程，重新加载模型并建立空 KV 缓存，没有跨档前缀复用，也没有每档额外预热。模型加载和全篇分词发生在计时区间之外；没有强制清除 macOS 文件缓存，所以这也不是统一的冷启动测试。

**输入处理速度（prefill TPS）**为输入 token 数除以完整输入处理耗时。程序以 2,048-token 块填充 KV，最后处理剩余输入并计算第一个候选输出的 logits，等待相关 MLX 数组完成计算后结束计时。输入块处理时有低频进度记录，其少量开销包含在输入处理时间内。

**生成速度（decode TPS）**为 128 除以生成区间耗时。完整输入处理后，每步选择一个非 EOS token，将它送入模型，计算下一步 logits，并同步等待计算完成，共执行 128 步。这个计数方式与此前 `ds4-bench` 的解码前向计算计数对齐，包含首个解码计算的等待，没有只挑最快的一段。

这里的“首个解码计算”发生在完整输入处理之后，不是 API 请求的首字延迟。测试没有 HTTP、排队、聊天模板或 Agent 工具调用，也没有把模型加载、分词和进程启动计入 TPS。其结果不能直接替代实际聊天服务的端到端延迟。

## 输入处理与生成速度

以下每档只有一轮正式测量，均生成 128 tokens。数值不是多轮平均值或中位数。

| 输入 tokens | 输入处理 tokens/s | 输入处理耗时（秒） | 生成 tokens/s | 生成耗时（秒） |
| ---: | ---: | ---: | ---: | ---: |
| 8,192 | 667.01 | 12.28 | 14.45 | 8.86 |
| 32,768 | 463.65 | 70.67 | 12.03 | 10.64 |
| 65,536 | 317.45 | 206.45 | 8.41 | 15.22 |
| 131,072 | 193.16 | 678.57 | 5.92 | 21.62 |

8K 到 128K，生成速度下降约 **59.0%**。输入处理速度从 667.01 降到 193.16 tokens/s，下降约 **71.0%**；输入长度增加时，完整输入处理时间也明显增加。64K 到 128K 的输入长度翻倍，输入处理时间从 206.45 秒增至 678.57 秒，约为原来的 3.29 倍，不能按短输入速度做线性估算。

128K 档的完整输入处理加上 128-token 生成，合计约 **700.18 秒，即 11 分 40 秒**，仍未包含加载和分词。对于这次“长输入、短输出”的工作负载，输入处理占据了主要时间；仅看“生成约 6 tokens/s”会漏掉前面的长时间等待。

原始记录还保存了排除首个解码计算后的速度：8K、32K、64K、128K 分别为 14.48、12.15、8.53、6.02 tokens/s。换用这个口径后，长上下文下生成变慢的现象仍然存在。但单轮顺序测试不足以把降速单独归因于某一种计算、缓存或持续负载因素。

## 内存与 KV 缓存

| 输入 tokens | MLX 峰值分配（GiB） | 解码结束时 KV 分配（GiB） |
| ---: | ---: | ---: |
| 8,192 | 35.10 | 1.65 |
| 32,768 | 39.98 | 6.53 |
| 65,536 | 46.58 | 13.03 |
| 131,072 | 59.93 | 26.03 |

MLX 峰值分配包含模型和推理数组，不包含其他应用与操作系统的全部内存。KV 是其中一部分，而且表中的 KV 值取自解码结束时，不能把两列再相加。它们也不等于系统监视器里的整机内存占用或进程 RSS。

本次权重配置为 52 层、8 个 KV heads、head dimension 128，BF16 每个元素占 2 字节。按完整 K/V 计算，每个缓存 token 的主体约为：

```text
52 层 × 2（K 与 V）× 8 heads × 128 × 2 字节
= 212,992 字节 = 208 KiB
```

仅 131,072-token 输入的 K/V 主体就约为 26 GiB；实测解码结束后的 KV 分配为 26.03 GiB，还包含后续解码和分块分配的空间。这解释了为什么权重已经做了 8bit 量化，长上下文仍然会额外占用大量内存。它不等于对降速原因的完整定位。

监控每 5 秒采样供电和内存状态，正式轮共记录 208 次采样，均显示交流电供电、内存压力正常。swap 始终为 1,896.38 MiB，没有增长；已有 swap 不等于本次新增换页。结束时系统未报告温度或性能警告，四档均正常退出。

监控保留了保护条件：掉电、严重内存压力、连续三次压力警告，或单档 swap 比基线增长超过 512 MiB 时停止。采样不能覆盖两次检查之间的全部瞬时变化，系统没有报告温度警告也不等于已经证明整段测试中完全没有频率变化。

## 复测时需要固定什么

这次测试没有通过 oMLX 的 HTTP 服务调用模型，而是复用其已有 Python 环境，直接执行 MLX-LM。完整运行器负责逐档启动进程、监控和保存记录；每档的核心逻辑如下，属于计时流程示意：

```python
# 全篇分词、模型加载在计时外；每档重新启动进程。
prompt = tokenize(corpus, add_special_tokens=False)[:input_tokens]
cache = make_empty_kv_cache(model)

prefill_start = timer()
prefill_all_but_last_token(prompt, cache, step_size=2048)
logits = forward(prompt[-1], cache)
next_token = argmax_excluding_eos(logits)
synchronize()
prefill_seconds = timer() - prefill_start

decode_start = timer()
for _ in range(128):
    emitted_token = next_token
    logits = forward(emitted_token, cache)
    next_token = argmax_excluding_eos(logits)
    synchronize()
decode_seconds = timer() - decode_start
```

要复测这组结果，需要同时固定权重版本与精度、推理库版本、语料 SHA-256、输入长度、128-token 输出预算、非 EOS 贪心选择、输入处理块、BF16 KV、独立进程和上述同步计时方式。只指定模型名和上下文长度，还不足以建立同口径的对照。

本次归档了汇总 CSV、逐档结果 JSON、128-token 输出、供电与内存采样、模型配置和 tokenizer 指纹，以及运行脚本 SHA-256。模型分片记录了大小与修改时间，没有在这次测速中重算全部分片的 SHA-256，因此不能把它写成一次完整权重校验。原始文件保留在本机工作区，未随本文上传；文中的流程示意也不代表已提供完整可下载的复现环境。

## 结论的适用范围

这轮数据确认：在本机、当前 MLX 实现、8bit 权重和 BF16 KV 配置下，Nanbeige4.3-33B 可以完成 128K 输入与 128-token 解码；从 8K 到 128K，输入处理和生成均明显变慢，128K 的主要等待发生在输入处理阶段。

还有几项边界需要保留：

- 每档只有一轮，且测试顺序固定，没有倒序复测、随机化顺序或统计置信区间；
- 每档只生成 128 tokens，未覆盖长时间输出、并发服务或多轮 Agent 运行；
- 没有统一系统文件缓存状态，也没有独立记录风扇设置、完整后台负载和 GPU 频率，不能把所有差异都归为上下文长度的单独作用；
- 原始正文续写中观察到重复内容，本次没有计算内容质量分数，不能据此声称长文理解或聊天表现良好；
- 原模型卡标称支持最高 [524,288 tokens（512K）](https://huggingface.co/Nanbeige/Nanbeige4.3-33B)，本文只测到 131,072-token 输入，没有验证本机 512K 的可用性；
- 本文没有验证 8bit 相对 BF16 的能力保持程度，也没有复现任何官方 Agent 榜单成绩。

这些数字可以作为本机后续测试的吞吐基线。要评估实际聊天或代码 Agent 的使用体验，还需要在相应模板、采样设置、上下文复用和工具调用流程下单独测量。
