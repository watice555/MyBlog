# DwarfStar 本机测速：M5 Max 上的 Qwen3.8 Flash Next Q4

这次用 [DwarfStar（antirez/ds4）](https://github.com/antirez/ds4)在本机运行
Qwen3.8 Flash Next Q4，关注两个问题：输入从 1K 增加到接近 256K 后，prefill 和生成
速度如何变化；开启 MTP 后，实际能加速多少。

测试于 2026 年 10 月 14 日完成。第一轮使用 DwarfStar 自带的意大利文长文本，随后
用中文和英文分别重测。三种语料都完成了普通解码与 MTP 测试，每种语料有 16 个正式
档位，共 48 个正式档位。

最需要先说明的是：**各档都重新建立 KV，没有前缀复用；但没有统一操作系统文件缓存
和 SSD n-gram 数据的缓存状态。** 每档每模式也只正式测了一轮。因此，本文记录的是
本机运行基线，不能仅凭这些数字认定 MTP 必然拖慢 prefill，或中文天然比英文更快。

## 环境与模型

- 机器：Apple M5 Max，18 核 CPU、40 核 GPU、128 GB 统一内存；
- 系统：macOS 27.0.1，arm64；
- 推理后端：Metal，单并发；
- 模型文件：`Qwen3.8-Flash-Next-Q4.gguf`，约 165.11 GiB；
- prefill chunk：2,048 tokens；
- 电源：AC 供电，运行期间用 `caffeinate -i` 防止空闲睡眠；
- 风扇：手动控制为 100%，以最大转速运行；
- Mac 运行状态：没有其他高占用程序，保留浏览器、IM、自动化任务等常驻程序，模拟日常使用环境；
- 使用原生上下文，没有启用 YaRN 扩展。

GGUF 的文件大小不等于需要常驻的内存。根据
[DwarfStar 的 Qwen3.8 说明](https://github.com/antirez/ds4/blob/fc80bd695da76ee14bcb86820bf900a5cdfda806/docs/QWEN38_FLASH_NEXT.md)，
Q4 的常驻权重约 69.74 GiB，95.37 GiB 的 BF16 n-gram 表留在 SSD 上，运行时按需
读取选中的行。这也意味着，SSD 读取和系统文件缓存是性能测量中需要考虑的因素。

## 输入长度、语料和计时口径

模型原生上下文为 262,144 tokens。测试的实际输入长度是：1,024、4,096、8,192、
16,384、32,768、65,536、131,072 和 261,856 tokens。

表里的“接近 256K”实际是 **261,856-token 输入**，没有把输入直接填满原生上限。
MTP 在本次基准中每轮最多提交 2 tokens：8 轮预热加 128 轮计时，最多需要 272 个
输出位置，另留 16 个位置余量，分配总量恰好是 262,144。

三份语料如下：

- 中文：[Project Gutenberg《红楼梦》](https://www.gutenberg.org/ebooks/24264)。
  去掉网站说明、许可和正文前的目录等内容，用 OpenCC `t2s` 转为简体，保留从
  “此开卷第一回也”开始的连续正文；模型分词后共有 683,721 tokens。
- 英文：[Project Gutenberg《白鲸》](https://www.gutenberg.org/ebooks/2701)。
  同样去掉网站说明和正文前的内容，保留从 “Call me Ishmael.” 开始的连续正文；
  分词后共有 303,870 tokens。
- 意大利文：DwarfStar 自带的 `speed-bench/promessi_sposi.txt`，共有
  383,792 tokens，作为第一轮上游语料基线。

中文和英文都没有重复拼接短段落来凑长度。输入按同一模型的 token 数对齐，字符数和
字节数并不相同。三份文本的内容、作者和年代也不同，所以跨语料差异同时包含内容
差异，不能单独归因于语言。

使用上游 `speed-bench/session_concurrency_bench`，具体流程为：

1. 每种模式先跑一个 1K 预热档，这个档位不计入正式结果。
2. 每个正式档位新建空会话，从语料开头处理指定长度的完整前缀。
3. prefill 结束后先进行 8 轮解码预热，再计时 128 轮。
4. 使用排除 EOS 的贪心生成。普通模式每轮产生 1 token，MTP 按实际提交的
   tokens 计数；两种模式的输出总长度和计时起点可能略有不同。
5. 全程顺序运行，一个大型模型进程退出后才启动下一轮。

输入直接使用正文 tokens，没有聊天模板或问答指令，输出是正文续写。
**Prefill 不含模型加载与分词时间；生成 TPS 使用 `decode_wall_tps`，包含 token
选择和模型计算，不含 HTTP、网络或聊天服务的其他开销。** 表中的 prefill 耗时也不
等于聊天 API 的完整首 token 延迟。

中文先测普通模式、再测 MTP；英文先测 MTP、再测普通模式。反转顺序只能减少固定
先后顺序带来的偏差，不能替代交错重复测量。

## 中文结果

下表每组数字均按“**普通 / MTP**”排列。生成提升按 MTP TPS 除以普通 TPS 减一

| ---: | ---: | ---: | ---: | ---: |
| 1024 | 1242.87 / 1095.53 | 0.824 / 0.935 | 55.28 / 61.92 | 12.0% |
| 4096 | 1305.11 / 1172.26 | 3.138 / 3.494 | 53.57 / 60.81 | 13.5% |
| 8192 | 1301.67 / 1193.91 | 6.293 / 6.861 | 53.57 / 59.69 | 11.4% |
| 16384 | 1282.60 / 1195.98 | 12.774 / 13.699 | 53.35 / 56.32 | 5.6% |
| 32768 | 1246.56 / 1180.82 | 26.287 / 27.750 | 52.67 / 55.83 | 6.0% |
| 65536 | 1227.54 / 1167.64 | 53.388 / 56.127 | 52.54 / 63.52 | 20.9% |
| 131072 | 1201.50 / 1138.19 | 109.090 / 115.159 | 51.71 / 54.96 | 6.3% |
| 261856 | 1151.10 / 1091.86 | 227.483 / 239.826 | 50.46 / 50.58 | 0.2% |

普通生成从短输入的约 55 tok/s 降至最大档的约 50 tok/s；prefill 则从约
1,200–1,300 tok/s 降至约 1,150 tok/s。中文最大档普通模式等待输入处理约
3 分 47 秒，MTP 模式约 4 分钟。

MTP 的收益没有随上下文长度单调变化：64K 档提高约 21%，而最大档几乎没有提高。
这更适合解释为不同续写位置的草稿接受情况不同，不能据此认定 64K 是 MTP 的最佳
上下文长度。

## MTP 收益为什么有限，prefill 又为什么变慢

MTP 需要先产生预测草稿，再由主模型验证。一次验证能提交多个 tokens，才有机会摊薄
开销；草稿没有被接受时，额外计算仍然发生。因此，“平均每轮多产生一些 tokens”
不等于生成速度按同样比例提高。

中文最大档的日志记录，MTP 每轮平均提交约 1.42 tokens；普通模式每轮计算约
19.8 ms，MTP 约 28.0 ms。提交 token 数增加约 42%，每轮计算耗时也增加约 42%，
两者几乎抵消，最终生成速度只有 50.46 → 50.58 tok/s。

中文各档开启 MTP 后，测得的 prefill 吞吐下降约 5%–12%，长上下文主要下降约 5%。
例如 32K 多花 1.463 秒，128K 多花 6.069 秒，最大档多花 12.343 秒。

**这些是测量到的差异，尚不是 MTP 导致该差异的因果证据。** 核对本次版本的代码后，
Qwen prefill 仍通过主模型前向路径处理输入，没有逐个输入 token 额外运行一遍 MTP
预测层。英文也没有一致的同幅度降速。具体差异是否来自运行顺序、系统缓存、持续
负载、内存布局或其他因素，本次没有做进一步隔离。

因此，评价 MTP 应看“prefill 加生成”的总耗时。按本次结果，长输入、短输出时，
生成阶段的小幅收益可能抵不过 prefill 多花的时间；长输出则更有机会抵消这部分
差异。这是对当前测量的使用建议，不能直接外推到其他文本或长时间生成。

## 缓存控制：做了什么，缺少什么

KV 缓存与系统文件缓存需要分开看。

- **KV 前缀复用已排除。** 每档新建空会话，重新处理完整前缀，没有 live KV 或
  磁盘 KV checkpoint 复用。
- **预热流程相同，缓存状态未必相同。** 每种模式都有一个 1K 预热档，但这不能
  保证 128K、256K 输入涉及的全部 n-gram 数据已经进入缓存。
- **系统缓存没有统一。** 不同模型进程顺序运行，macOS 可能保留前一轮读取过的
  模型文件页和 n-gram 数据。没有主动建立统一冷缓存，也没有把完整语料预热到经
  验证的稳定状态，没有记录缓存命中率或 SSD 实际读取量。
- **只有单轮正式结果。** 没有多轮均值、中位数、方差或置信区间；短档尤其容易
  受到调度和计时波动影响。

如果以后要确认 MTP 对 prefill 的真实影响，应先用相同完整输入充分预热，保留每档
重新建立 KV 的条件，再按“普通 → MTP → MTP → 普通”交错测多轮。还需要统一输出
计时窗口或实际输出长度，并比较中位数和波动。**本次没有执行这组补充实验。**

## 内存与完成情况

中文和英文的四个基准进程都以退出码 0 结束，四个内存采样器也正常退出。原始 CSV
共 36 档，包括四个预热档，全部状态为 `ok`；剔除预热后得到 32 个正式档位。
意大利文的两个进程及其 18 档（含两个预热档）同样通过。

中文和英文测试约每 10 秒采样一次内存，内存压力等级始终为正常（1），swap 使用
固定为 332.56 MiB，没有增加；系统 wired 内存采样峰值约 85.59 GiB。结束时
`pmset -g therm` 未记录温度或性能警告，但这不等于证明 GPU 频率完全不变。

引擎在最大档规划的内存约 81.1 GiB，包含约 69.73 GiB 常驻权重。进程峰值
footprint 普通模式约 21.94 GiB、MTP 约 23.57 GiB，**不能将这两个数字当作模型
总内存**：共享 mmap 和 Metal 权重并不完整计入单个进程 footprint。原始 CSV 的
`footprint_gib` 还是工具估算的会话内存，也没有当作实测总占用使用。

最大档能够完成 prefill 和这段续写，说明本机在本次条件下能运行接近 256K 的输入。
本文没有测长上下文问答、检索准确率或其他质量指标，也没有测试 YaRN 扩展到更长
上下文。不能把“跑完了”解释为长上下文质量已经验证。

## 复现与原始记录

在本地 ds4 仓库中，中文 MTP 的基准参数如下。其余轮次替换语料路径和输出文件名，
普通模式去掉 `--spec`。首个重复的 `1024` 是需要排除的预热档。

```sh
make -j8 session-concurrency-bench

/usr/bin/time -l /usr/bin/caffeinate -i \
  ./speed-bench/session_concurrency_bench \
  -m gguf/Qwen3.8-Flash-Next-Q4.gguf \
  --prompt-file runtime/qwen38-context-bench-zh-en-20261014/zh-corpus.txt \
  --concurrency 1 \
  --ctx 1024,1024,4096,8192,16384,32768,65536,131072,261856 \
  --gen 128 --warmup 8 --prefill-chunk 2048 --spec \
  --csv runtime/qwen38-context-bench-zh-en-20261014/recheck-zh-mtp.csv
```

以上命令复现的是基准参数，不会自动统一系统缓存，也不会自动排除 CSV 中的预热行。
复测时应使用新的输出文件名，避免工具以追加方式混入旧结果。

引擎基于上游提交 `fc80bd695da76ee14bcb86820bf900a5cdfda806`，此次测试没有修改
推理代码。意大利文轮次的本地提交为 `9e13a30645f7d1c082d3315d628f650ccfd51d8b`，
中文、英文轮次为 `dc7a01c0477e09bf0a243af6f36e3b28d54a24bd`，两者之间仅增加了
测试记录。

原始资料保存在 ds4 仓库的以下目录，未复制为博客附件：

- `runtime/qwen38-context-bench-20261014/`：意大利文 CSV、日志、汇总及内存记录；
- `runtime/qwen38-context-bench-zh-en-20261014/`：中文与英文语料、CSV、日志、
  汇总、内存记录和运行状态；
- 各目录的 `metadata.json` 保存语料 SHA-256、模型校验值及测试条件，
  `summary.csv` 保存剔除预热后的结果。
